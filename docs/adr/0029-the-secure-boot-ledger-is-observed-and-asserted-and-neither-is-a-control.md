# The Secure Boot ledger is one observed half and one asserted half, and neither is a security control

## Status

accepted

## Context

ADR 0008 scopes the Secure Boot enrolment task to machines that are **not
currently enforcing Secure Boot**, and states why in the task's own
description: a machine that is enforcing does not trust this server's kernel,
so it cannot boot FOS, so it cannot run the task that would make it trust us.
The task that would enrol the key cannot run on the machine that needs it.

That constraint was written down and then had nowhere to live. Nothing in FOG
recorded what state any machine was in, so finding the eligible machines meant
an administrator guessing — and a wrong guess is not a clean failure. It
schedules a task against a machine that PXE boots, refuses the kernel, and
reboots. What the administrator sees is a host that did not image, which looks
like a broken image or a broken network, not like a task that was never
eligible in the first place.

The obvious place to learn a machine's firmware state is FOS, which already
computes it: `sbState()` in `usr/share/fog/lib/secureboot-funcs.sh` returns one
of five words. But FOS only runs when someone schedules a task, and the whole
problem is deciding what to schedule. A host stays unknown until FOS runs,
which may be months away or never — the same shape as architecture before
schema step 369.

iPXE runs on every PXE boot, and it can already read the answer. EFI variables
are exposed as a settings scope (`interface/efi/efi_settings.c`), FOG's own
iPXE configuration enables it on EFI builds, and `default.ipxe` is generated by
the installer rather than embedded in the binary — so reporting the state costs
two lines in a generated file and no change to fog-ipxe or to FOS.

## Decision

### 1. Two halves, and they are different kinds of fact

The ledger is not one thing. It is an **observation** and an **assertion**, and
conflating them is how a record stops meaning anything.

| | Observed (`hostSbState`, `hostSbStateTime`) | Asserted (`hostSbEnrolled`, `hostSbEnrollCert`, `hostSbEnrollVia`) |
|---|---|---|
| What it is | what a machine said about itself | a record that somebody enrolled something |
| Written by | iPXE on every PXE boot; FOS when the enrolment task runs | FOS for the `db` and MOK paths; a human for the USB path |
| Editable | **never**, in the UI or over the API | **yes**, and it has to be |
| Timestamp | stamped by the server from its own clock | the date of the enrolment, which may be historical |

The observed half is never editable because there is no such thing as a
correct manual value for it: it is a report of what happened on a boot, and a
human typing one is not correcting a mistake, they are inventing an
observation. Enforcement is `Route::$serverOwnedFields['host']` — which
refuses the write with a 400 and is pinned by
`tests/api-server-owned-fields.test.php` — plus disabled (not readonly) inputs
on the host form, because a disabled input is not submitted at all.

The asserted half is editable because enrolment happens three ways and only
two of them can write it themselves. A technician at the machine with a USB
stick reports nothing; leaving the field hand-editable is the only thing that
makes that path recordable at all.

### 2. HARD: neither half may ever be read as a security control

`service/ipxe/boot.php` is unauthenticated by necessity — a booting NIC has no
credential to present — so everything in the observed half is
attacker-controlled. The asserted half carries even less authority, because a
human typed it.

**Both halves exist for targeting, filtering and display. Nothing may ever
read either as a security control.**

The property that makes this safe is the asymmetry of what a lie buys:

- Spoofing `disabled` (or leaving the state unknown) gets a host a task that
  cannot work. That is a wasted task — which is exactly what happens today, on
  every host, with no record at all. Nothing regresses.
- Spoofing `enforcing` gets a host *excluded* from an enrolment it would
  otherwise receive. It costs nothing, because the enrolment is not a
  privilege and the host is denying it to itself.

There is no third case, and there must not be. Specifically: the boot decision
keeps reading the live request and never this column, exactly as step 369
already requires for `hostArch`; `IpxeBootMenu::_filterMenus()` keeps gating
the Secure Boot menu entries on the live `${platform}`; and no authentication,
authorization or trust decision anywhere may consult either half.

### 3. Six states, in FOS's vocabulary, not four in a new one

The stored values are `FOG\Boot\SecureBootState`'s constants. Five are taken
verbatim from FOS's `sbState()` so that two reporters cannot drift into two
vocabularies for one fact; `unknown` is the sixth and is server-side only.

| | |
|---|---|
| `unknown` | nothing has reported yet |
| `nonefi` | booted BIOS/CSM; Secure Boot is not a concept here |
| `noefivars` | UEFI, but the variables could not be read |
| `setup` | Setup Mode — `db` is writable, enrolment is unattended |
| `enforcing` | User Mode, Secure Boot ON — the task cannot run |
| `disabled` | User Mode, Secure Boot OFF — the ADR 0008 case |

**`setup` and `disabled` are not collapsed into one "off".** Turning Secure
Boot off leaves the platform key in place, so `db` still refuses a write; only
Setup Mode accepts one. The Secure Boot configuration page already says this in
as many words, and `fog.enrollsb` branches on exactly it. It is the difference
between an enrolment that finishes with nobody at the keyboard and one that
needs a human at the MokManager screen — which is the single most useful thing
an administrator can know before scheduling, and a four-state model throws it
away.

`unknown` is likewise not a synonym for anything. Collapsing it into `disabled`
is the dangerous direction, because `disabled` is the value that makes a host
look like a valid target.

### 4. The parse lives in one place, and the format was measured

`SecureBootState::fromBootRequest()` is the only code that understands the wire
format, and `tests/secureboot-state-classifier.test.php` is the only place it
is asserted. The values it keys on were measured on 2026-08-28 rather than
taken from documentation:

| Rig | `platform` | `${efi/SecureBoot}` | `${efi/SetupMode}` |
|---|---|---|---|
| QEMU, `OVMF_CODE.secboot.fd` + plain `OVMF_VARS.fd` | `efi` | `00` | `01` |
| QEMU, firmware with no Secure Boot support | `efi` | *(empty)* | *(empty)* |
| QEMU + SeaBIOS + FOG's own `ipxe.lkrn`, real `default.ipxe` | `pcbios` | *(empty)* | *(empty)* |

Two consequences that are not obvious and are load-bearing:

**The legacy BIOS path cannot break.** `EFI_SETTINGS` is gated on
`PLATFORM_efi`, so the `efi` scope is never registered on a BIOS build; iPXE
substitutes an empty string for a setting it cannot resolve rather than
erroring; and `param` accepts a key with no value. Measured, not reasoned:
FOG's own `ipxe.lkrn` ran this exact `default.ipxe` through to the chain.

**An absent param and an empty param are different facts.** The wire form from
that BIOS run was
`…&platform=pcbios&secureboot=&setupmode=` — the parameters are present and
empty, so `filter_input()` returns `''`. A server that has not re-run the
installer since this shipped sends neither, and returns `null`. That is what
lets a not-yet-upgraded server read as `unknown` instead of masquerading as
legacy BIOS, and it is why the classifier treats the two separately.

### 5. The record references what was enrolled, not just when

`hostSbEnrollCert` holds the SHA-256 of the enrolled certificate. An enrolment
date alone goes stale in silence: FOG has PKI zones, a multi-server CA and
certificates that expire, so "enrolled 2026-03-14" says nothing about whether
the machine trusts what this server is serving today — which is the question
an administrator actually has.

This costs one column and no new computation, because both sides of the
comparison already exist and already agree. `FOGConfigurationPage::secureBoot()`
renders `strtoupper(implode(':', str_split(hash_file('sha256', $cert), 2)))`,
and FOS's `sbCertFingerprint()` is `sha256sum | toupper | colon-split` over the
same DER file. The check is string equality.

### 6. A staged MOK request is not an enrolment

`fog.enrollsb` has three exits — already-trusted, enrolled-via-`db`, and
staged-a-MOK — and all three end with the same argument-free completion POST.
The server cannot tell them apart, so FOS reports the outcome explicitly to
`service/secureboot.report.php` before completing.

The distinction is not bookkeeping. Recording "enrolled" for a staged MOK is a
lie an administrator acts on: they turn Secure Boot on in firmware, and the
machine stops booting, because nothing ever confirmed the key at MokManager.
So `mok-pending` is its own value and the grid renders it as pending rather
than as a date. `mok` is reserved for a human recording that they worked
through MokManager, which is the only point at which it is true.

`trusted` is likewise its own value and not a synonym for `db`. It means the
machine already trusted this certificate when the task ran, and nothing
observed how it got there — a `db` write, a MOK confirmed months ago, or an
image that shipped with it. Folding it into `db` would assert a mechanism
nobody watched happen, which is the same mistake in a quieter register.

The five stored values are therefore `db`, `trusted`, `mok`, `mok-pending` and
`manual`; the host form whitelists exactly those and refuses anything else, so
the column cannot fill up with `usb`, `USB stick` and `Dave did it`.

### 7. Last write wins, and provenance is shown rather than arbitrated

When a technician's hand-entered date and a later task report disagree, the
later fact wins, with no precedence rule in either direction. A technician
correcting a wrong machine-written record is legitimate, and a rule that let
the machine outrank the human would create a value nobody could fix.

What makes that safe is showing where the value came from instead of
adjudicating it: `hostSbEnrollVia` is rendered beside the date, so "enrolled
2026-03-14 (entered by hand)" and "(reported by task)" are visibly different
claims.

### 8. The task refuses a target it cannot run on — but not a guess

`Host::createImagePackage()` refuses a single-host enrolment task whose target
last reported `enforcing`, `nonefi` or `noefivars`. This is the payoff: it
turns ADR 0008's constraint from something a technician remembers into
something the server checks.

`unknown` is **allowed through**, deliberately. Nothing is reported until a
host PXE boots, so refusing it would make the task unusable on every existing
fleet until a full boot cycle had happened — in exchange for preventing the one
thing that already happens today on every such host, a wasted task. The host
list column and its sort are what keep an unknown host from *looking* eligible;
the refusal is only about stopping an administrator who asks anyway, and only
a positively-reported bad state is refused.

**The refusal is written twice because there are two code paths.** A
non-imaging group task never calls `Host::createImagePackage()` — it batch-
inserts over the member ids — so `Group::createImagePackage()` carries its own
check. It **filters** rather than throwing: a group is a mixed bag by nature,
ADR 0008 gives the task `ttIsAccess='both'` precisely so a batch in the same
state can be scheduled at once, and refusing a whole group because one member
came back from a firmware change with Secure Boot already on would make the
group path useless for the case it exists for. Both call the same
`SecureBootState::refusalReason()` so the two cannot say different things.

## Consequences

- Two schema steps, 376 and 377, five additive NULL-able columns on `hosts`,
  no data migration. Separate steps rather than one so a partial failure leaves
  an unambiguous state, the same reasoning as 369/370.
- Two lines in `configureDefaultiPXEfile()`. Servers that do not re-run the
  installer keep an older `default.ipxe`, send neither parameter, and read as
  `unknown` — which is the safe direction, and clears itself on the next
  install. `tests/netboot-host.test.sh` asserts both parameters against the
  written file, in iPXE's exact spelling, and asserts they sit above the
  `net1..net7` chain that short-circuits to `:bootme` on a single-NIC machine.
- `generateIpxeItems()` excludes all five columns. FOG's record of what a
  machine reported has no business being echoed back at that machine, and
  nothing in the menu consumes it.
- A new machine entry point, `service/secureboot.report.php`. It is narrowed to
  hosts with a Secure Boot enrolment task actually in flight — true by
  construction when FOS calls it — so that "advisory" does not become "writable
  by anyone who knows a MAC". It answers 200 in every case including refusal,
  because a non-2xx from a FOS script is invisible to the caller.
- `hostLastPing` and `hostLastCheckin` are added to
  `Route::$serverOwnedFields['host']` in the same change. The host form has
  always disabled those inputs and its comment has always called them
  server-owned, but the API never refused them — a rule enforced by one form is
  a rule that holds until someone adds a second writer.
- Companion changes in `FOGProject/fos` are required for the automatic half:
  `fog.enrollsb` must report which of its three branches it took, plus the
  fingerprint it already computes and prints. Until that ships, the observed
  half works on its own and the enrolment record is hand-entered only.
- ADR 0008 is unchanged and remains the authority on what the task is for. This
  ADR is the record, not the task.
